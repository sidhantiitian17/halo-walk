Generated by `analysis/train_classifier.py` on 2026-11-16 22:12:17. Every number below is read from `eval.json`.

## Data

* 628 labelled flows from 24 complete DATAGEN batches (r01, r02, r03, r04, r05, r06, r07, r08, r09, r10, r11, r12, r13, r14, r15, r16, r17, r18, r19, r20, r21, r22, r23, r24). Flows per class: call 96, gaming 96, streaming 72, bulk 46, other 318.
* Each batch is one recorded session with its own random link rate, ports, packet sizes/rates and IPv4/IPv6 mix. Flow records (`ctl/raw_flows.jsonl`, written by the controller with `--collect`) are joined to the generator labels (`labels.jsonl`) on the 5-tuple (protocol, LAN address/port, WAN address/port), only within the same batch.
* Features are computed by the very functions the controller uses at runtime (`halo.classifier.feat1/feat2`): protocol, first 8 packet sizes with direction, inter-arrival times, and rate-shape statistics over the first h conntrack intervals. No addresses, ports, payload or TTL.

## How we evaluated (and why)

Flows from the same session share conditions (link rate, host, generator parameters). Splitting flows or packets at random would let the model recognise the session instead of the traffic class, which inflates scores (Arp et al., USENIX Security 2022; Zhao et al., SIGCOMM 2025). So whole batches are held out:

* **Split:** leave-batches-out GroupKFold, k=5 (group = DATAGEN batch/session); calibration = 25% of training batches, group-disjoint, inside each training fold.
* Inside each training fold, a separate group of batches is used only to fit the calibration; the test batches are never seen by fitting or calibration.
* XGBoost, 150 trees, depth 4, learning rate 0.1, class-balanced weights, fixed seed, single thread (deterministic).
* The deployed decision is the stage-2 model after h=2 conntrack intervals; all classification numbers use the calibrated probabilities that are actually deployed.

## Caveats

* Split unit = batch (one DATAGEN session: own link rate, ports, sizes, v4/v6). No flow of a test batch is used for fitting or calibration; calibration batches are disjoint from fit batches inside every training fold.
* Classification metrics use argmax of the CHOSEN-calibrated probabilities (what the controller deploys); ML 'decision' carries no abstain, the promote metrics apply policy.tin_for with p >= 0.90.
* Deployed decision = stage 2 at h=2 conntrack bins (bins are poll deltas, not exactly 1 s). Stage-2 model is ONE model over h in (2, 4, 6) (h is a feature); per-horizon rows exist only for flows with len(bins) >= h.
* Heuristic: abstain -> 'other'. `tot` (elephant rule) is not in raw_flows.jsonl; it is reconstructed as the sum of recorded conntrack deltas (all recorded bins, <= 8): a lower bound of the runtime counter. A stricter variant using only the first 2 bins gives macro-F1 0.463.
* Calibration choice is made on pooled out-of-fold TEST ECE (as specified); with only two candidates this is a mild selection effect on the reported chosen ECE.
* Joined flows: 628; label lines without a collected flow: 0 (of which call/gaming UDP over IPv6: 0); collected flows without a label (dropped): 0.
* Not modelled in the promote metrics: the controller's demote-on-behaviour guard and the Voice-share shield (policy.admit_voice), both of which can only remove promotions.
* Stage-1 is evaluated on the first 8 recorded packets; at runtime predict1 may fire at age > 1 s with fewer packets (only for slow flows).
* Distribution of recorded bins per flow: {2: 123, 3: 61, 4: 24, 5: 81, 6: 339}.
* Synthetic generators (halo/gen.py) only: results describe separability of these generators under this rig, not real applications.
* Zero wrongful ML promotions out of 436 non-interactive flows: 95% upper bound 0.008 (Clopper-Pearson, ignoring batch clustering) - absence of errors in this sample, not proof of zero risk.
* TTL/hop-limit values observed in the data: [61, 63]. If TTL is constant per direction in this rig, the ablation cannot show a leak here (direction is already in the signed size); real homes with mixed OSes (TTL 64/128/255) could still leak device identity.
* Deployed stage-2 temperature T=1.073 (fit on r06,r10,r11,r12,r15,r23); CV-fold temperatures ranged 1.030-1.298, so the deployed calibration is not identical to the evaluated ones.
* TTL ablation: macro-F1 with TTL 0.933 vs without 0.933 (gap +0.000).
* Generator-artefact probe: the first upstream TCP payload packet is gen.py's request line, whose length differs by client (bulk always requests 2**40 bytes -> constant length). With that one size masked, macro-F1 is 0.850 (bulk F1 0.624) vs 0.933 unmasked (bulk F1 0.923). Call vs gaming are separated mainly by the generators' non-overlapping packet-size ranges in scenarios/run.py.
